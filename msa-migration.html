Case 01 · AI-native migration

AI 에이전트와 함께 3개 레거시 백엔드의 구독 도메인을 단계적으로 MSA로 통합하다.

기존 클라이언트 계약을 유지하면서, 실제 운영 트래픽을 받는 구독 전용 서비스로 API를 옮겼습니다.

Context

구독 책임이 세 레거시 백엔드에 흩어져 있었습니다.

데이트팝의 구독 기능은 서로 다른 기술 스택의 세 백엔드에 나뉘어 있었습니다. 같은 구독 사용자와 상태를 다루면서도 API 계약과 예외 처리, 데이터 접근 방식이 달라 변경 범위를 추정하기 어려웠습니다.

목표는 한 번에 모든 코드를 다시 쓰는 것이 아니었습니다. 운영 중인 클라이언트를 바꾸지 않고 검증 가능한 API 묶음부터 전용 서비스로 옮겨, 실제 트래픽으로 새 경로의 안정성을 확인하는 것이었습니다.

제가 맡은 범위
마이그레이션 실행 책임자로서 이전 대상을 좁히고, 호출 경로와 계약을 비교하고, 구현을 검토한 뒤 운영 전환 결과를 확인했습니다.

Key decisions

전면 재작성보다 작은 운영 전환을 반복했습니다.

01

API 묶음 단위로 이전

의존성이 비교적 명확하고 운영 검증이 가능한 구간부터 옮겼습니다. 새 서비스가 우선 처리하고 기존 경로는 fallback으로 유지했습니다.

02

외부 계약을 고정

요청·응답과 인증 경계를 먼저 비교해 클라이언트 수정 없이 라우팅만으로 전환할 수 있게 했습니다.

03

AI와 책임을 분리

AI는 호출 경로 추적, 계약 비교, 구현 초안과 테스트 생성을 맡았습니다. 범위·위험 판단, 코드 리뷰와 운영 검증은 제가 맡았습니다.

After

Logs

이전한 API가 새 서비스 운영 로그에 남고 정상 응답하는 것을 확인했습니다.

Outcome

9개 API operation이 실제 운영 트래픽을 처리하고 있습니다.

클라이언트 변경 없이 일부 구독 경로를 전용 서비스로 전환했습니다. 프로젝트 전체는 진행 중이며, 현재 결과는 “완료”가 아니라 운영에서 검증된 첫 번째 이전 단위입니다.

이 경험을 통해 AI-native 역량은 코드를 더 빨리 생성하는 능력보다, 넓은 레거시 경로를 빠르게 좁히고 사람이 검증 가능한 단위로 바꾸는 능력에 가깝다는 것을 배웠습니다.
