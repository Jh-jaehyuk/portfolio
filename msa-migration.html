Case 01 · Service extraction

클라이언트 계약을 깨지 않고 구독 기능을 하나씩 전용 서비스로 옮겼어요.

클라이언트는 그대로 두고, 실제 운영 트래픽을 받는 구독 전용 서비스로 API를 옮겼어요.

Context

구독 기능이 세 레거시 백엔드에 흩어져 있었어요.

같은 구독 사용자와 상태를 다루면서도 기술 스택과 API 계약, 예외 처리, 데이터 접근 방식은 서로 달랐어요. 그래서 작은 변경도 어디까지 영향을 주는지 가늠하기 어려웠어요.

모든 코드를 한 번에 다시 쓰지는 않았어요. 클라이언트를 바꾸지 않아도 되는 API 묶음부터 전용 서비스로 옮기고, 실제 트래픽으로 새 경로를 확인했어요.

제가 맡은 범위
이전 대상을 좁히고 호출 경로와 계약을 비교한 뒤, 구독 전용 서비스의 API를 직접 구현했어요. ALB·Terraform 변경은 권한 보유자가 적용했고, 배포 후 라우팅과 운영 로그 확인도 제가 맡았어요.

Key decisions

한 번에 다시 쓰기보다, 작은 전환을 반복했어요.

01

API 묶음부터 옮겼어요

의존성이 분명하고 운영에서 확인할 수 있는 구간부터 옮겼어요. 이전한 API만 새 서비스가 처리하고, 미이전 경로는 기존 서비스에 남겼어요.

02

외부 계약은 그대로 뒀어요

요청·응답과 인증 경계를 먼저 비교해, 클라이언트 수정 없이 라우팅만 바꿀 수 있게 했어요.

03

탐색은 도구로 줄이고 구현은 직접 했어요

세 저장소에 걸친 호출 경로와 계약 차이를 Codex·Claude Code로 좁혀, 남은 시간을 무엇을 먼저 옮길지 정하는 데 썼어요. 구현과 이전 범위 판단, 운영 검증은 제가 맡았어요. 초안에서 좌표를 못 찾았을 때 (0, 0)을 그대로 돌려주는 부분을 되돌린 적이 있어요. 호출부가 “좌표 있음”으로 판정해 거리 계산을 건너뛰면서 전체 목록이 거리 필터에서 탈락하는 문제였어요.

After

우선 라우팅과 기존 경로를 나눠 안전하게 옮길 수 있는 경로를 만들었어요.

데이터 경계는 아직 나누지 않았어요
이번 단위는 조회 API라 스팟·매장·결제 같은 공용 테이블은 레거시와 그대로 공유해요. 구독 전용 테이블만 새 서비스가 소유하고, 쓰기 이전과 소유권 분리는 다음 단계로 남겼어요. 그래서 이 작업은 전면 재작성이 아니라 경로 단위 추출에 가까워요.

Verification

코드가 끝났다는 말보다 운영 경로의 증거를 확인했어요.

Routing

새 서비스 우선

이전한 API가 새 서비스로 먼저 전달되는 구성을 인프라 정의에서 확인했어요.

Health

운영 서비스 정상

배포 후 서비스가 운영 환경에서 정상 상태를 유지하는지 확인했어요.

Logs

실제 요청 200

이전한 API가 새 서비스 운영 로그에 남고 정상 응답하는지 확인했어요.

“같은 응답인가”를 사람 눈으로 보지 않게 만들었어요

이전 전후 응답을 자동으로 비교하되, 원본이 버그라서 일부러 다르게 구현한 경우를 구분해야 했어요. 그냥 두면 의도한 차이와 이관 실수가 같은 실패로 섞여요.

그래서 판정을 네 갈래로 나눴어요. 차이가 없고 선언도 없으면 통과, 차이가 있는데 선언이 없으면 이관 버그로 실패, 차이와 선언이 함께 있으면 예상된 발산으로 통과예요. 그리고 선언은 있는데 차이가 사라진 경우도 실패로 처리했어요.

죽은 선언을 남겨 두면, 그 경로에서 나중에 생긴 진짜 발산까지 “예상된 차이”로 묻혀요. 그래서 선언이 쓸모없어지면 반드시 지우도록 실패로 만들었어요.

Outcome

API 9개가 실제 운영 트래픽을 처리하고 있어요.

클라이언트 변경 없이 일부 구독 경로를 전용 서비스로 전환했어요. 전체 마이그레이션은 아직 진행 중이에요. 지금의 결과는 완료가 아니라, 운영에서 확인한 첫 번째 이전 단위예요.

이 전환에서 가장 중요했던 건 코드를 빨리 만드는 일이 아니라, 넓은 레거시 경로를 운영에서 확인할 수 있는 작은 단위로 좁히는 일이었어요.
