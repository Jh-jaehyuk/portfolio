Case 02 · Performance

30초 넘게 타임아웃되던 응답을 1초 미만으로 줄였어요.

같은 계정과 데이터로 배포 전후를 측정하고, 운영 환경과 실제 앱 화면까지 확인했어요.

Before
30초+ timeout
Production
주로 300~500ms
Rows loaded
약 1/1,000

Problem

문제는 느린 API보다 보이지 않는 화면이었어요.

‘내가 찜한 목록’ API는 응답이 30초를 넘기며 요청이 실패했어요. 앱은 데이터를 받지 못해 목록 화면을 제대로 그리지 못했어요.

모든 사용자에게 생기는 문제는 아니었어요. 찜 목록에 담기는 매장의 결제 이력은 편차가 극단적이라, 상위 한 곳이 그다음 매장의 열 배, 보통 매장의 백 배를 넘어요. 그래서 특정 매장을 찜한 사용자에게서만 재현됐고, 평균적인 목록으로 테스트하면 보이지 않았어요.

목표를 막연히 “빠르게”로 잡지 않았어요. 사용자가 실제로 화면을 볼 수 있도록 타임아웃을 없애고, 같은 데이터 조건에서 1초 안에 응답하도록 정했어요.

측정 방법과 범위
응답 시간은 Postman에서 같은 사용자 계정과 데이터로 수정 전후를 반복 요청해 확인했어요. 수정 후 모든 측정이 1초 안에 끝났고, 300~500ms는 운영 배포 직후 검증 구간에서 주로 확인한 값이에요.
데이터 접근량은 별도로 확인했어요. 수정 전후 코드를 같은 합성 데이터에 올려 같은 응답이 나오는 것을 확인한 뒤, 실행된 쿼리 수와 애플리케이션이 읽어 들인 행 수를 셌어요. 공개 자료에는 배수만 싣고 실제 건수는 제외했어요.

Root cause

선조회가 비용만 내고 쓰이지 않고 있었어요.

목록 쿼리만 봐서는 병목이 보이지 않았어요. serializer와 도메인 메서드까지 따라가자, 결제 이력을 통째로 미리 읽어 두면서도 정작 응답을 만들 때는 그 데이터를 쓰지 않고 다시 조회하고 있었어요. 상품이 걸린 관계가 서로 달라 선조회한 값이 닿지 않는 경로였어요.

Fix

필요 없는 적재를 걷어내고, 집계는 DB에 맡겼어요.

01

실제 소비 경로를 따라갔어요

view의 queryset에서 멈추지 않고, serializer와 도메인 메서드가 응답 필드를 만드는 과정까지 확인했어요.

02

원본 대신 집계값을 가져왔어요

결제 원본을 통째로 읽던 선조회를 걷어내고, 상품별 판매량은 Subquery로 DB에서 집계해 값만 받았어요.

03

선조회한 값이 닿게 만들었어요

도메인 메서드가 관계를 다시 조회하는 대신, 이미 읽어 둔 잔액·상품을 그대로 쓰도록 바꿨어요.

Validation

환경별 확인을 실제 사용자 화면까지 이어갔어요.

앱실제 찜 목록 화면빈 화면이던 찜 목록이 정상 노출로 복구

Secondary example

큰 테이블을 읽는 다른 조회도 같은 방식으로 줄였어요.

구매자 정보 조회에서는 조건과 인덱스 사용 방식을 바꿔, 실행 계획이 훑던 행을 1만분의 1 수준으로 줄였어요. 메인 사례의 응답 시간과는 별개의 개선이에요.

Outcome

숫자만 줄이지 않고, 사용자 화면까지 되살렸어요.

30초 넘게 걸리던 API는 측정한 요청이 모두 1초 안에 응답했고, 운영에서는 주로 300~500ms가 나왔어요. 같은 계정과 데이터로 배포 전후를 비교했고, 운영 배포 뒤 앱 화면이 제대로 보이는 것까지 확인했어요.
