Case 04 · Performance

30초 타임아웃을 500ms 이하로 줄여 앱 화면을 복구하다.

동일한 계정과 데이터 조건으로 배포 전후를 측정하고, 운영 환경과 실제 앱 노출까지 확인했습니다.

Before
30초+ timeout
Production
주로 300–500ms
User impact
앱 화면 복구

Problem

느린 API가 아니라 보이지 않는 화면이 문제였습니다.

‘내가 찜한 목록’ API는 응답에 30초 이상 걸려 쿼리 타임아웃이 발생했습니다. 앱은 데이터를 받지 못해 목록 화면을 제대로 그리지 못했습니다.

성능 목표는 추상적인 “빠르게”가 아니었습니다. 사용자가 실제로 화면을 볼 수 있도록 타임아웃을 제거하고, 같은 데이터 조건에서 1초 미만으로 응답하게 만드는 것이었습니다.

측정 방법
Postman에서 동일한 사용자 계정과 데이터 조건으로 수정 전후를 반복 요청했습니다. 수정 후에는 주로 300~500ms였고 모든 반복 측정이 1초 미만이었습니다.

Root cause

직렬화 과정에 반복 DB 조회가 숨어 있었습니다.

목록 쿼리 자체만 보면 병목이 명확하지 않았습니다. 응답을 만드는 serializer와 도메인 메서드까지 추적하자, 각 항목이 같은 관계와 계산 데이터를 반복 조회하는 N+1 형태의 비용이 드러났습니다.

Request path

List query찜 목록 조회
↓ 항목마다 반복 ↓
Serializer관계 데이터 재조회
↓ 누적 비용 ↓
Result30초 이상 · timeout

Fix

필요한 관계를 한 번에 읽고, 이미 읽은 데이터로 계산했습니다.

01

실제 소비 경로 추적

view의 queryset에서 멈추지 않고 serializer와 도메인 메서드가 응답 필드를 만드는 과정까지 확인했습니다.

02

관계 데이터 선조회

필요한 단일·다중 관계를 select와 prefetch로 미리 불러와 항목별 추가 조회를 제거했습니다.

03

메모리 계산 재사용

같은 값을 다시 DB에서 읽지 않고 이미 로드된 관계 데이터로 응답 값을 계산했습니다.

Validation

환경별 확인을 실제 사용자 화면까지 이어갔습니다.

단계조건확인 결과
수정 전동일 계정·데이터, Postman30초 이상 소요 후 쿼리 타임아웃
로컬수정 코드 반복 요청모든 측정 1초 미만
스테이징같은 API와 데이터 조건정상 응답과 목록 데이터 확인
운영배포 직후 반복 요청주로 300~500ms
앱실제 찜 목록 화면빈 화면이 정상적으로 노출되는 목록으로 복구

Secondary example

큰 테이블을 읽는 다른 조회도 같은 방식으로 좁혔습니다.

구매자 정보 조회에서는 조건과 인덱스 사용 방식을 조정해 30만 건 이상을 훑던 실행 경로를 30건 미만 조회로 줄였습니다. 메인 사례의 응답 시간과는 별개의 개선입니다.

Rows examined

Before300,000+
↓ 조건 · 인덱스 정렬 ↓
After< 30

Outcome

성능 개선을 사용자 화면 복구로 끝맺었습니다.

30초 이상 걸려 타임아웃되던 API를 반복 측정에서 항상 1초 미만, 운영에서는 주로 300~500ms로 단축했습니다. 수치는 동일 계정과 데이터로 측정한 배포 전후 응답 시간이며, 운영 배포 후 앱 화면이 정상 노출되는 것까지 확인했습니다.
