CASE 1

영화 관람권 발급 데드락

2026.09 ~ 2026.10혼자 진행Python, MySQL

결제는 완료됐는데 영화 관람권 번호(핀)와 알림톡이 나가지 않는 일이 드물게 있었습니다. 같은 에러 코드(1213)로 보이던 데드락 로그를 롤백된 SQL 기준으로 다시 나눠 데드락 원인 두 가지와 실패를 놓치던 처리 하나를 찾고, 제휴사 연동 서버, 어드민 환불, 결제 서버 세 곳을 고쳤습니다. 마지막 수정 후 40일간 데드락은 0건입니다.

맡은 범위
로그 재분류, 서비스 세 곳 수정, 운영 분포를 본뜬 로컬 MySQL 재현, 배포 후 측정
선택
환불 조회는 인덱스를 강제하지 않고, 대상 id를 단일 조건으로 먼저 모은 뒤 그 id로만 잠금. 한 쿼리로 두면 잠금 범위가 옵티마이저의 인덱스 선택에 달리기 때문

원인과 수정

원인수정
같은 결제의 동시 발급"기록 삭제 후 삽입"이 빈 간격에 잠금을 걸어 두 요청이 서로를 기다림. 결제 행을 먼저 잠그고 비교하도록 변경: 없으면 저장, 같은 핀이면 무시, 다른 핀이면 실패
어드민 일괄 환불의 OR 조건결제 id 또는 주문번호로 핀을 찾는 OR 조건이 ref_or_null로 풀려 미배정 핀 인덱스 전체를 잠금. 단일 조건 조회 두 번으로 대상 id를 모은 뒤 id로만 잠그도록 분리
실패가 조용히 지나감결제 서버가 발급 실패를 경고 로그만 남기고 성공 처리. 연동 서버는 1213이면 최대 2회 재시도, 결제 서버는 결과를 모를 때 같은 주문번호로 1회 재호출(이미 배정된 핀을 그대로 돌려받음)

원인을 나눈 방법

  • 데드락 로그는 모두 "Deadlock found when trying to get lock"으로 시작해, 이 줄만 세면 원인이 하나로 보임
  • 로그가 남은 8월 19일부터 수정일까지의 데드락 로그를, 바로 다음 줄에 남는 롤백된 SQL 기준으로 다시 묶음. 발급 경로는 발급 기록 INSERT와 미배정 핀 배정 UPDATE 두 묶음으로 나뉘고, 나머지는 관람권 사용 처리 경로
  • UPDATE 데드락과 같은 시각을 찾아 어드민 일괄 환불이 겹쳐 있었던 것을 확인하고, 환불 쿼리의 실행 계획에서 ref_or_null과 십수만 행 예상치를 확인
  • 같은 추적 중 결제 서버가 발급 실패를 성공으로 처리하던 것을 발견, 세 번째 수정 대상으로 추가

가설 정정: 로컬 재현

처음에는 시각이 가장 가까운 환불 완료 표시 UPDATE를 상대로 봤습니다. 운영 분포(전체 핀 대비 미배정 핀 비율)로 로컬 MySQL 8.0에 데이터를 만들고, 환불 쪽 쿼리와 발급 UPDATE를 겹쳐 각각 10번씩 실행했습니다.

발급과 겹친 쿼리실행 계획, 데드락
환불 완료 표시 UPDATE기본 키 전체 스캔, 10번 중 0번 (대기만 생기고 순환은 없음)
같은 UPDATE, 인덱스 강제ref_or_null, 10번 중 10번
PG 환불 전 핀 잠금 SELECT FOR UPDATEref_or_null, 10번 중 10번
수정 후 (id로만 잠금)기본 키로 대상 핀 2개만 잠금, 10번 중 0번

재현 결과로 데드락 상대를 표시 UPDATE에서 환불 전 잠금 SELECT로 정정. 두 쿼리가 같은 조건 함수를 쓰고 있어 한 번의 수정이 양쪽에 적용됨

검증과 결과

  • 동시 발급 수정: 수정 전 방식은 로컬에서 1213 재현. 수정 후 서로 다른 결제 50건 병렬 실행 모두 성공, 같은 결제에 핀 순서를 바꿔 20번 동시에 보내도 기록은 한 행
  • 마지막 수정 배포(10월 8일) 후 40일간 연동 서버 데드락 0건
  • 정리하면서 같은 원칙을 다시 적용해, 아직 문제가 난 적 없는 다른 제휴처의 핀 매칭 OR 조건도 실행 계획 확인 후 같은 방식으로 수정

자세한 과정: team.datepop.co.kr/posts/ticket-pin-deadlock

CASE 2

동시 결제 초과 판매 차단

2026.11혼자 진행Python, MySQL, Redis

잔여 수량이 1개 남은 상품을 서로 다른 두 사용자가 동시에 결제하면 둘 다 승인되는 문제가 있었습니다. 세 PG 승인 경로가 PG 승인 직전에 같은 공통 승인 검사를 거치도록 바꿨고, 운영 6개월치 결제를 다시 실행한 재현에서 초과 판매 경합을 모두 막았습니다. 배포 후 7일간 잘못 막힌 결제는 없었습니다.

맡은 범위
원인 분석, 공통 승인 검사 설계와 구현, 세 PG 경로 적용, 잔여 수량 계산식 공통화(공통 라이브러리와 서비스 5곳), 0원 결제 후속 수정
선택
매장 단위 잠금은 잔여 수량 재계산과 승인 예약 기록에만 걸고, PG 호출은 잠금 밖에 둠. 같은 매장 결제가 PG 응답을 기다리며 줄 서지 않게 하기 위함
트레이드오프
Redis 장애 중에는 검사 없이 통과시키고 에러 로그만 남김. 그동안은 경합을 막지 못하지만, 경합은 드물게 일어나므로 Redis 장애로 결제 전체가 멈추는 쪽을 피함. 대신 검사를 건너뛰면 바로 장애 알림이 가도록 함

고른 방법과 버린 방법

방법판단
결제 준비 단계 검사 강화결제 완료 기록이 PG 승인 뒤, 잠금 밖에서 생김. 준비 단계에서는 두 결제가 모두 잔여 1개를 보고 통과
기존 사용자 단위 잠금 유지서로 다른 사용자의 결제는 같은 잠금을 잡지 않아 직렬화되지 않음
PG 승인까지 매장 잠금 안에서 처리같은 매장 결제가 PG 응답 시간만큼 대기. PG마다 완료 기록 시점(승인 응답, 웹훅)도 달라 잠금 안에 묶기 어려움
승인 직전 매장 잠금, 재계산, 승인 예약잠금은 쿼리 몇 번 동안만 유지. 승인 대기 결제를 잔여 수량에 미리 반영해, PG 승인 사이의 경합도 다음 검사에서 보이게 함

원인

  • 잔여 수량 검사가 결제 준비 단계에만 있고, 승인 단계에서는 다시 검사하지 않음
  • 잔여 수량은 결제 완료와 취소 요청 상태만 셈. 결제창을 연 결제는 잔여 수량을 점유하지 않음
  • 잠금이 사용자와 상품, 또는 주문 단위라 서로 다른 사용자의 결제는 직렬화되지 않음
  • 결제 완료 기록이 PG 승인 뒤 잠금 밖에서 생김(PG A는 승인 응답 처리 중, PG B는 웹훅 도착 시). 잠금 단위만 바꿔서는 해결되지 않음

공통 승인 검사의 동작

  • 매장 잠금(같은 잔여 수량을 나눠 쓰는 매장 그룹 포함)을 정해진 순서로 획득. 3초 안에 못 얻으면 거절
  • DB 세션을 새로 시작해 최신 데이터로 잔여 수량 재계산
  • 재계산은 결제 완료, 취소 요청, 그리고 승인 예약 중 아직 결제 전인 결제를 SQL 한 문장으로 합산. 결제 전에서 완료로 바뀌는 순간에도 한 번만 차감
  • 통과하면 승인 대기 결제로 예약하고, 예약은 30분 뒤 자동 만료
  • 거절 조건은 잔여 부족과 잠금 대기 초과 두 가지뿐. 잔여 수량을 쓰지 않는 상품, 강제 결제, 이미 완료된 결제, Redis 오류는 기존처럼 통과

PG별 적용

PG거절 시점과 처리
PG APG 승인 요청 전에 거절, 품절로 실패 기록. 카드 승인 자체가 일어나지 않음
PG B결제 승인 요청 전에 거절, 결제 실패 처리. PG B가 승인을 거절하면 예약 해제
PG C주문 잠금 안의 결제 확정 단계에서 거절. 기존 자동 취소 경로로 연결

배포 전 검증

  • 공통 승인 검사가 없으면 실패하는 테스트를 먼저 작성해, 대상 파일 5개에서 21건 실패 확인 후 구현
  • 검사 단위 테스트: 잔여 1개에 승인 대기 결제가 있으면 거절, 대기 결제가 실패하면 통과, 완료된 예약 결제는 한 번만 차감, 구매 수량이 잔여보다 크면 거절, 잠금 대기 초과는 거절, Redis 오류는 통과
  • PG 경로 테스트: PG A와 PG B는 거절 시 PG 승인이 호출되지 않는지, PG C는 결제 완료 대신 자동 취소로 가는지 확인
  • 기존에 성공하던 결제를 막는 변경이라, 운영 복제본에서 2026년 5월부터 11월까지의 결제를 다시 실행해 새로 막히는 결제를 셈. 모두 실제 초과 판매 경합이었음

같이 고친 것

  • 잔여 수량 계산식이 결제 서버 2곳, 앱 서버 14곳, 어드민, 배치, 구독 서버에 복제돼 있었고, 일부는 구매 수량을 빠뜨려 2개 구매를 1개로 계산. 공통 라이브러리에 규칙 하나로 모으고, 다섯 서비스가 같은 함수를 쓰도록 변경
  • Redis 다운(2분 지속)과 검사 우회 로그(1건)를 장애 알림으로 연결하고, 알림 본문에 우회 중 승인된 결제에서 환불 대상을 찾는 조회를 넣음
  • 0원 결제(포인트, 쿠폰 전액)는 PG 승인을 거치지 않아 검사를 우회. 같은 매장 잠금 안에서 결제 기록을 저장하도록 후속 수정. 같은 6개월 재현에서 새로 막히는 0원 결제 0건

배포 후 확인

  • 배포 후 7일간 잘못 막힌 결제 0건 (검사 거절 로그 0건, 같은 기간 결제 로그는 정상 수집)

CASE 3

구독 서비스 분리와 서비스 간 쓰기

2026.07 ~ 현재구독 API 이전, 캠페인 아웃박스 설계Python, Litestar, MySQL, Celery

Go와 Django 레거시에 흩어져 있던 구독(팝패스) API를 새 구독 서비스로 옮겼습니다. 기존 응답과 새 응답을 비교하며 API 단위로 경로를 바꿔, 앱과 웹은 고치지 않았습니다. 서비스를 나누며 생긴 "DB가 달라 한 트랜잭션으로 묶을 수 없는 쓰기"는 트랜잭셔널 아웃박스로, 되돌릴 수 없는 PG 환불이 낀 즉시 해지는 보상 트랜잭션으로 처리했습니다.

맡은 범위
구독 API 이전(조회, 가입과 최초 결제, 결제 수단, 정기 결제 재시도와 갱신 배치), 캠페인 서비스 아웃박스 설계와 워커, 사용자 즉시 해지의 보상 트랜잭션 적용과 수동 재시도
선택
아웃박스 행을 기준으로 두고 큐 메시지는 워커를 깨우는 신호로만 사용. 메시지가 유실돼도 스케줄러가 멈춘 행을 다시 넣음
트레이드오프
서비스 간 쓰기는 워커가 처리한 뒤 반영되는 최종 일관성

고른 방법과 버린 방법

버린 방법문제와 고른 방법
캠페인 서비스가 매장 DB에 직접 쓰기서비스 분리의 첫 단계라 다른 도메인 DB에 붙지 않기로 함. 주문과 같은 트랜잭션에 할 일을 아웃박스로 적고, 워커가 마일리지 내부 API를 호출
큐 메시지만으로 전달커밋 후 발행 전에 죽거나 메시지가 유실되면 요청이 사라짐. 행이 기준, 메시지는 신호
환불 호출 후 바로 해지 완료PG 환불은 되돌릴 수 없고 응답이 불명확할 수 있음. 해지 접수와 아웃박스를 한 트랜잭션에 기록하고, 환불 성공 또는 이미 환불됨을 확인한 뒤에만 완료
요청마다 새 주문번호로 최초 결제PG가 클라이언트 주문번호를 그대로 받아, 같은 요청이 두 번 가면 두 번 결제됨. 사용자, 상품, 날짜로 만든 멱등 키를 결제 서버가 검사. 같은 날 해지 후 재가입은 막히지만 이중 청구보다 낫다고 판단

API 이전 방식

  • 조회 API부터 시작해 계정과 탐색, 가입 사전 검사, 발권 취소, 결제 수단, 가입과 최초 결제, 정기 결제 재시도와 갱신 배치 순으로, 결제가 걸린 경로를 마지막에 이전
  • 같은 요청을 기존 서버와 새 서버에 보내 응답을 비교하는 스크립트에 경로를 하나씩 등록하고, 차이를 확인한 뒤 경로 규칙으로 전환
  • 비교 중 기존 배포본에 남아 있던 차이(무력화된 필터, 구독자 판정 오류)도 발견해 새 서비스에서 복구
  • PG 호출은 결제 서버로 위임. 구독 서비스는 소유권과 상태만 판단하고, 카드번호 복호화와 빌키 해지는 결제 서버가 담당. 암호화 키를 구독 서비스에서 빼 카드 데이터를 다루는 곳을 하나로 줄임
  • 정기 결제 재시도와 갱신 배치가 대상 조회 SQL과 연장 처리를 글자 단위로 두 벌 갖고 있던 것을 하나로 모으고, 실제로 다른 세 가지(대상 범위, 재시도 창, 실패 처리)만 인자로 분리

사용자 즉시 해지의 보상 트랜잭션

  • 관리자 환불에 쓰던 보상 트랜잭션을 사용자 즉시 해지로 확장하고, 요청 출처(사용자, 관리자)를 구분
  • 접수 시 구독 상태, 티켓 상태, 취소 이력, 아웃박스를 한 트랜잭션으로 기록. 환불 성공 또는 이미 환불됨을 확인한 뒤에만 해지 완료로 전환
  • 자동 재시도를 다 쓰면 검토 필요 상태로 남기고 실패 큐로 이관. 관리자 수동 재시도는 새 요청을 만들지 않고 기존 요청을 다시 대기로 돌리며, 중복 호출, 처리 중, 내용 불일치는 거절
  • 접수, 성공, 처리 중, 실패 큐 상태 전이를 단위와 계약 테스트로 검증하고, 관리자 환불과 기간 말 해지 회귀 테스트를 함께 실행

아웃박스를 두 DB에서 같이 쓰기

  • 기존 아웃박스 워커는 로그 DB 하나를 하드코딩하고 있어, 요청 종류마다 어느 DB와 모델을 볼지 정하는 바인딩으로 바꿔 캠페인 DB 아웃박스도 같은 워커와 재처리 로직으로 처리
  • 워커가 걸러 바로 버리는 실수(전체 URL 저장, 환경값 누락)는 아웃박스 기록 함수에서 미리 막도록 고정

숙박 예약 신규 구축

2026.09 ~ 2026.11예약 도메인, 고객용과 사장님용 웹 담당Python, Litestar, MySQL, Redis, Next.js

데이트팝 상품은 결제하면 바로 이용권이 나가는 구조라 체크인과 체크아웃, 숙박일별 재고, 사장님 승인이 필요한 숙박을 담을 수 없었습니다. 예약 도메인을 새로 설계해 연박 객실 선점, 결제 확정, 취소와 환불, 자동 취소를 만들고, 고객용 숙박 웹과 사장님 예약 확인 화면까지 맡았습니다.

맡은 범위
예약 원장과 상태 전이 이력, Redis 객실 선점, 결제 확정, 취소와 환불, 환불 아웃박스, 주기 작업, 이용 완료 연결, 고객용 숙박 웹, 사장님 예약 확인과 판매 캘린더
선택
선점은 10분 뒤 저절로 풀리는 임시 상태라 Redis에, 확정된 예약은 DB 원장에 둠. 결제 확정은 원장 커밋, 매장 재고 차감, 선점 해제 순서로 하고, 결과가 불명확하면 결제 id로 다시 조회해 한 결과로 수렴
트레이드오프
선점(Redis)과 예약(DB)이 나뉘어, 결제 도중 실패하면 정리되지 않은 점유가 남을 수 있음. 주기 작업이 DB와 Redis를 다시 읽어 누수된 점유를 회수

설계 판단

주제판단
연박 선점숙박일별 객실 수량 검사와 점유를 Lua 한 번으로 처리해 모든 날을 잡거나 아무것도 잡지 않음. 같은 매장의 키는 해시 태그({shop_id})로 한 슬롯에 묶어 클러스터에서도 Lua가 여러 키를 함께 다룰 수 있게 함. 같은 선점 id 재시도는 같은 결과, 내용이 다르면 거절
확정 실패선점 만료, 재고 부족, 판매 중지면 예약을 취소로 기록하고 전액 환불 요청을 같은 트랜잭션의 아웃박스에 적재
사장님 승인승인 기한을 체크인 시각 한 곳에서 계산. 기한이 지나면 주기 작업이 자동 취소와 전액 환불
고객 취소 환불결제 후 1시간 이내면 전액, 그 외에는 체크인까지 남은 달력일 기준 고정 일정(5일 이상 100%, 하루 줄 때마다 20%씩, 당일 0%). 취소 당시 매장 취소 정책도 스냅샷으로 함께 저장

기존 시스템과 잇기

  • 예약 상태가 바뀔 때마다 알림톡을 아웃박스로 적재하고, 체크인 전날 안내와 체크아웃 후 방문 완료 처리는 주기 작업으로 실행
  • 방문 완료 때 결제를 이용 완료로 전환하는 처리를 추가해, 리뷰와 정산 같은 기존 기능이 숙박에도 그대로 동작
  • 환불은 예약 서비스가 아웃박스에 적고 결제 서버의 숙박 환불 내부 API가 실행. 환불률 0% 취소도 결제 취소로 정산되도록 아웃박스를 발행

운영 중 보완

  • 점유 누수 정리: 예약이 취소나 반려로 끝났거나, 예약 없이 선점만 만료된 점유를 회수. 판정은 매장별 잠금 안에서 DB와 Redis를 다시 읽어 확정, 결제 확정과 겹치지 않게 함
  • 실패 큐에서 다시 처리돼 성공한 환불이 예약 쪽에는 실패로 남아 있던 것을 찾아, 같은 멱등 키로 환불 행과 아웃박스를 대조해 상태를 다시 맞춤
  • 상태 전이마다 누가, 왜 바꿨는지를 필수로 남기는 이력 테이블을 둠
