Case 02 · Product system

제휴 매장당 월 1회 무료 마케팅을, 사장님이 앱에서 직접 운영하게 만들다.

사장님 앱 리뉴얼의 경쟁 포인트를 시간과 상태로 움직이는 백엔드 운영 시스템으로 구현했습니다.

Benefit
매장당 월 1회
Flow
7단계 상태
Status
앱 연동·QA 진행

Business context

제휴의 가치를 사장님이 직접 체감할 기능이 필요했습니다.

셀프마케팅은 사장님 앱 리뉴얼에 추가되는 기능입니다. 데이트팝과 제휴한 매장은 매달 한 번 무료 마케팅을 신청하고, 모집부터 체험과 평가까지 앱에서 확인할 수 있습니다.

이 기능의 목적은 단순한 캠페인 신청 화면이 아니었습니다. “제휴하면 매달 고품질 마케팅을 받을 수 있다”는 경험을 만들어 경쟁 서비스와 구분되는 제휴 가치를 제공하는 것이었습니다.

제가 맡은 범위
백엔드 구현을 책임졌으며, 핵심 도메인 모델과 캠페인 생성 구간은 팀원과 함께 개발했습니다. 저는 진행 상태 계산, 응답 계약, 운영 규칙과 검증 흐름을 중심으로 맡았습니다.

State model

화면 목록이 아니라 운영 수명주기를 모델링했습니다.

01–03신청 → 검수 → 모집
04–06선정 → 체험 → 평가
07완료

Key decisions

정책의 기준을 서버 한 곳에 두었습니다.

01

시간 + 상태 계산

캠페인 상태값만 반환하지 않고 모집·선정·체험·평가 기간을 함께 계산해 현재 단계를 결정했습니다.

02

서버 주도 화면 계약

현재 단계, 안내 문구, 가능한 행동, 비활성 사유를 서버가 반환해 iOS와 Android의 정책 차이를 막았습니다.

03

매장 단위 월 제한

사장님 계정이 아니라 제휴 매장을 기준으로 활성 캠페인을 제한하고, 완료 후에도 월말까지 다음 신청을 막았습니다.

Why server-driven

정책 변경을 앱 배포 주기에서 분리했습니다.

앱이 상태별 문구와 행동을 각각 구현하면 iOS와 Android가 다른 경험을 제공할 수 있습니다. 단순한 안내 문구 수정도 앱 업데이트와 심사가 필요합니다. 그래서 정책과 문구를 서버 응답으로 통일했습니다.

Verification

출시 전 화면 대신 계약과 상태 전이를 검증했습니다.

공개할 수 없는 출시 전 앱 화면은 사용하지 않습니다. 각 상태를 가진 테스트 매장 데이터로 백엔드 응답을 확인하고, 앱 팀이 같은 계약으로 화면을 그릴 수 있도록 상태 도식만 공개합니다.

Contract

응답 필드

현재 상태와 문구, 행동 가능 여부가 상태별로 일관되게 반환되는지 확인했습니다.

Transition

시간 경계

기간 시작·종료와 상태값 조합에 따라 다음 단계로 올바르게 이동하는지 검증했습니다.

Integration

진행 상태

백엔드 핵심 구현은 완료됐고 앱 연동과 QA가 진행 중입니다. 현장 테스트용 데모 앱은 더미 데이터 기반으로 준비될 예정입니다.

Outcome

운영 정책을 여러 앱이 소비할 수 있는 하나의 계약으로 바꿨습니다.

아직 출시 성과를 주장할 단계는 아닙니다. 현재 확인된 결과는 복잡한 캠페인 수명주기와 월별 이용 제한을 백엔드에서 일관되게 표현하고, 앱이 상태 표현에 집중할 수 있는 기반을 만든 것입니다.

제품 요구를 API 목록으로 바로 옮기지 않고, 시간이 흐르며 변하는 상태와 정책의 책임을 먼저 정한 경험이었습니다.
