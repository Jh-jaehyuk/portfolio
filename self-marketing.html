Case 05 · Product system

매달 한 번 무료로 받는 마케팅을 사장님이 직접 운영하게 만들었어요.

사장님 앱 리뉴얼의 경쟁 포인트를 시간과 상태로 움직이는 백엔드 시스템으로 만들었어요.

Benefit
매장당 월 1회
Flow
내부 7상태
Status
앱 연동·QA 진행

Business context

제휴하면 무엇이 좋은지 사장님이 바로 느낄 수 있어야 했어요.

제휴 매장은 매달 한 번 무료 마케팅을 신청할 수 있어요. 모집부터 체험과 평가까지 모든 과정을 앱에서 확인해요.

단순히 캠페인을 신청하는 화면을 만드는 일은 아니었어요. “제휴하면 매달 좋은 마케팅을 받을 수 있다”는 경험으로 경쟁 서비스와 다른 가치를 보여주려 했어요.

제가 맡은 범위
백엔드 구현을 맡았고, 핵심 도메인 모델과 캠페인 생성은 팀원과 함께 개발했어요. 저는 진행 상태 계산과 응답 계약, 운영 규칙과 검증 흐름을 중심으로 맡았어요.

State model

화면 목록보다 캠페인이 흘러가는 과정을 먼저 그렸어요.

01–03신청 → 검수 → 모집
04–06선정 → 체험 → 평가
07완료

Key decisions

정책의 기준은 서버 한 곳에 뒀어요.

01

시간과 상태를 함께 계산했어요

상태값만 돌려주지 않았어요. 모집·선정·체험·평가 기간을 함께 계산해 지금 어느 단계인지 결정했어요.

02

화면 정책을 서버가 알려줘요

현재 단계와 안내 문구, 가능한 행동, 비활성 사유를 서버가 내려줘요. iOS와 Android가 서로 다른 정책을 보여주는 일을 막았어요.

03

월 제한을 동시 요청에서도 지켰어요

사장님 계정이 아니라 제휴 매장을 기준으로 활성 캠페인을 제한했어요. 캠페인이 끝나도 월말까지는 다음 신청을 막았어요. 조회하고 만드는 사이에 요청이 두 번 들어오면 같은 달에 두 건이 생기기 때문에, 매장 단위 잠금을 먼저 잡고 트랜잭션 안에서 기존 캠페인 행까지 잠근 뒤에 검사했어요.

Why server-driven

정책 변경을 앱 배포 주기에서 떼어냈어요.

상태별 문구와 행동을 앱마다 구현하면 iOS와 Android가 다른 경험을 보여줄 수 있어요. 안내 문구 하나를 고쳐도 앱 업데이트와 심사가 필요해요. 그래서 정책과 문구를 서버 응답으로 통일했어요.

Verification

출시 전 화면 대신 계약과 상태 전이를 확인했어요.

공개할 수 없는 출시 전 앱 화면은 사용하지 않았어요. 상태별 테스트 매장 데이터로 백엔드 응답을 확인하고, 앱 팀이 같은 계약으로 화면을 그릴 수 있도록 상태 도식만 공개했어요.

Contract

응답 필드

현재 상태와 문구, 행동 가능 여부가 상태마다 일관되게 내려오는지 확인했어요.

Transition

시간 경계

기간 시작·종료와 상태값 조합에 따라 다음 단계로 제대로 이동하는지 확인했어요.

Integration

진행 상태

백엔드 핵심 구현은 끝났고 앱 연동과 QA를 진행하고 있어요. 현장 테스트용 데모 앱은 더미 데이터 기반으로 준비할 예정이에요.

Outcome

여러 앱이 함께 쓰는 하나의 운영 계약을 만들었어요.

아직 출시 성과를 말할 단계는 아니에요. 지금 확인한 결과는 캠페인의 전체 과정과 월별 이용 제한을 백엔드에서 일관되게 표현하고, 앱이 화면을 그리는 일에 집중할 기반을 만든 거예요.

제품 요구를 곧바로 API 목록으로 바꾸지 않았어요. 시간이 지나며 달라지는 상태와 정책을 누가 책임질지 먼저 정한 경험이었어요.
