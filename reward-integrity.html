Case 05 · Data integrity

사용량이 4배 늘어난 리뷰 보상 시스템의 정합성을 지키다.

복제 지연과 재계산 동시성, 교차 저장소 원장 반영 문제를 하나씩 불변식으로 바꿔 해결했습니다.

Context

보상 규모보다 어려운 것은 수정과 회수였습니다.

리뷰 보상 확대 프로젝트에서 전체 지급량은 전년 동일 기간 대비 4.4% 증가했지만 실제 사용량은 약 4배, 사용률은 23.8%에서 91.5%로 높아졌습니다.

이 수치는 프로젝트 전체 성과입니다. 제가 맡은 부분은 리뷰가 수정·삭제되거나 미디어 인증 상태가 바뀔 때 보상 원장과 리뷰 이력이 같은 결과를 가리키도록 만드는 일이었습니다.

핵심 불변식
같은 리뷰 상태에서 보상 재계산을 여러 번 실행해도 최종 잔액과 이력은 한 번 계산한 결과와 같아야 합니다.

Problem-solving timeline

한 번의 수정으로 끝내지 않고 다음 정합성 경계를 추적했습니다.

  1. 01

    Replica lag

    리뷰 수정 직후 지급 이력을 읽기 복제본에서 조회하면 방금 쓴 데이터가 보이지 않아 중복 판단이 틀릴 수 있었습니다. 즉시 판단이 필요한 조회를 writer DB로 옮겼습니다.

  2. 02

    현재 리뷰의 한도 오염

    Writer DB 조회만으로 충분하지 않았습니다. 수정 중인 리뷰의 기존 이력이 지급 한도 계산에 포함되면 정상적인 재지급까지 막았습니다. 현재 리뷰 ID를 한도 계산에서 제외했습니다.

  3. 03

    재계산 동시성

    미디어 상태가 동시에 바뀌면 이력을 덧붙이는 방식이 중복 결과를 만들 수 있었습니다. 리뷰 행을 잠그고 기존 계산 이력을 교체하도록 트랜잭션 경계를 정리했습니다.

  4. 04

    상태 변경과 원장 잔액

    이력의 상태만 취소로 바꿔서는 이미 지급된 잔액이 줄지 않았습니다. 회수액을 음수 offset 원장으로 기록하고, 이미 반영된 순액과 비교해 멱등적으로 보정했습니다.

Key decisions

각 문제를 데이터 불변식으로 고정했습니다.

01 · Consistent read

즉시 판단은 writer에서

쓰기 직후 보상 여부를 결정하는 경로는 복제 지연을 허용하지 않도록 일관된 읽기 경로를 사용했습니다.

02 · Serialized recalc

리뷰 단위 잠금

하나의 리뷰에 대한 재계산을 직렬화하고 이력을 append가 아닌 replace 방식으로 갱신했습니다.

03 · Ledger correction

음수 offset 원장

상태 플래그가 아니라 잔액을 실제로 바꾸는 보정 거래를 남겨 회수와 재실행 결과를 일치시켰습니다.

Cross-store consistency

하나의 transaction으로 묶을 수 없는 경계를 인정했습니다.

보상 원장과 리뷰 이력이 서로 다른 저장소에 있어 단일 데이터베이스 transaction으로 원자성을 보장할 수 없었습니다. 핵심 원장을 먼저 commit하고, 성공 후 이력을 동기화하며, 일일 정합성 작업으로 누락을 다시 맞추는 구조를 사용했습니다.

Outcome

정합성을 “중복 지급 방지”보다 넓은 문제로 다뤘습니다.

읽기 복제본을 writer로 바꾸는 첫 수정만으로 문제를 끝내지 않았습니다. 현재 리뷰의 한도 계산, 동시 재계산, 실제 잔액 회수와 교차 저장소 동기화까지 추적해 같은 입력의 재실행이 같은 최종 결과를 만들도록 개선했습니다.

운영형 보상 시스템에서는 상태값보다 원장의 순변화가 진실에 가깝고, 완벽한 분산 transaction보다 명확한 commit 순서와 반복 가능한 복구 절차가 더 현실적인 해법임을 배웠습니다.
