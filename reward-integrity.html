Case 03 · Data integrity

사용량이 약 4배 늘어난 뒤 드러난 리뷰 보상 정합성 문제를 해결했어요.

복제 지연과 재계산 동시성, 교차 저장소 원장 문제를 하나씩 불변식으로 바꿔 해결했어요.

Context

보상을 주는 것보다 고치고 회수하는 일이 더 어려웠어요.

리뷰 보상 확대 뒤 동일한 조건의 7일 비교에서 프로젝트 사용량이 약 4배 늘었어요. 사용량이 커지면서 수정·재계산·회수 경로에 숨어 있던 정합성 문제가 운영에서 드러났어요.

이 수치는 프로젝트 전체의 성과예요. 저는 리뷰가 수정·삭제되거나 미디어 인증 상태가 바뀌어도 보상 원장과 리뷰 이력이 같은 결과를 가리키게 만드는 일을 맡았어요.

핵심 불변식
같은 리뷰 상태라면 보상을 여러 번 다시 계산해도 최종 잔액과 이력은 한 번 계산한 결과와 같아야 해요.
재계산할 때 지금까지의 순 적립액을 먼저 구해서, 있어야 할 금액과 같으면 아무 행도 만들지 않아요. 다르면 그 차이만큼 음수 행으로 회수하고 다시 적립해요. 그래서 몇 번을 실행해도 결과가 같아요.

Problem-solving timeline

한 번 고친 뒤에도 다음 정합성 경계를 계속 따라갔어요.

  1. 01

    복제 지연

    리뷰를 고친 직후 읽기 복제본을 조회하면 방금 쓴 데이터가 보이지 않을 수 있었어요. 중복 판단이 틀리지 않도록 즉시 판단이 필요한 조회를 writer DB로 옮겼어요.

  2. 02

    현재 리뷰의 한도 오염

    Writer DB만 사용해도 충분하지 않았어요. 수정 중인 리뷰의 기존 이력이 지급 한도에 포함되면 정상적인 재지급도 막혔어요. 그래서 현재 리뷰 ID를 한도 계산에서 뺐어요.

  3. 03

    재계산 동시성

    미디어 상태가 동시에 바뀌면 이력을 덧붙이는 방식이 중복 결과를 만들 수 있었어요. 리뷰 행을 잠그고 기존 계산 이력을 교체하도록 트랜잭션 경계를 정리했어요.

  4. 04

    상태 변경과 원장 잔액

    이력 상태만 취소로 바꿔서는 이미 지급한 잔액이 줄지 않았어요. 회수액을 음수 offset 원장으로 남기고, 이미 반영한 순액과 비교해 다시 실행해도 같은 결과가 나오게 했어요.

Key decisions

발견한 문제를 데이터 불변식으로 고정했어요.

01 · Consistent read

즉시 판단은 writer에서

쓰기 직후 보상 여부를 정하는 경로에서는 복제 지연을 허용하지 않았어요. 일관된 읽기 경로를 사용했어요.

02 · Serialized recalc

보상 행이 아니라 리뷰 행을 잠갔어요

회수를 음수 행으로 쌓다 보니 한 리뷰에 적립 행이 여러 개 생겨요. 그래서 적립 행 하나만 잠그면 동시 재계산이 서로 다른 행을 잡고 둘 다 진행돼요. 집계도 잠금 없이 읽으면 오래된 스냅샷을 보고 이중 회수가 날 수 있고요. 재계산 시작 전에 리뷰 행을 먼저 잠가서 두 경우를 한 번에 막았어요.

03 · Ledger correction

음수 offset 원장

상태만 바꾸지 않고 잔액을 실제로 고치는 거래를 남겼어요. 회수와 재실행 결과도 같아졌어요.

Cross-store consistency

하나의 transaction으로 묶을 수 없는 경계도 인정했어요.

보상 원장과 리뷰 이력이 서로 다른 저장소에 있어 하나의 transaction으로 묶을 수 없었어요. 핵심 원장을 먼저 commit하고 성공한 뒤 이력을 맞췄어요. 빠진 데이터는 일일 정합성 작업으로 다시 맞췄어요.

Outcome

정합성을 중복 지급보다 더 넓은 문제로 바라봤어요.

읽기 복제본을 writer로 바꾸는 첫 수정에서 멈추지 않았어요. 현재 리뷰의 한도 계산, 동시 재계산, 실제 잔액 회수와 교차 저장소 동기화까지 따라갔어요. 같은 입력을 다시 실행해도 같은 최종 결과가 나오도록 개선했어요.

운영형 보상 시스템에서는 상태값보다 원장의 순변화가 실제 결과에 더 가까웠어요. 완벽한 분산 transaction보다 분명한 commit 순서와 반복 가능한 복구 절차가 더 현실적인 해법이라는 것도 배웠어요.
